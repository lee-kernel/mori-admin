# 后端编码规范（可选全栈底座）

适用于 `api/app` 与相关后端测试，整合了 Mori 的分层边界、API 契约、PostgreSQL 数据访问与安全约束。新增完整业务模块的操作步骤见 [模块开发指南](module-development.md)，局部 Agent 入口见 [api/AGENTS.md](../api/AGENTS.md)。

---

## 一、分层与职责边界

- **`main.py`**：只负责应用装配、生命周期（启动配置校验与 `init_db`）、中间件、全局异常处理器和业务路由注册。
- **路由层（`api.py`）**：只处理 HTTP 协议、参数校验、依赖注入、权限鉴权、异常到 HTTP 状态码的映射以及响应包装；**严禁在路由层写 SQL**。
- **服务层（`service/`）**：负责业务规则、状态转换和数据访问；**不返回 FastAPI `Response` 或 `ApiResponse`**，也不依赖前端展示细节。
- **Schema（`schemas.py`）**：请求与响应 Pydantic 模型放在对应模块的 `schemas.py`；仅跨模块共享的稳定响应结构（如 `ApiResponse`）放入全局 `app/schemas/`。
- **外部集成**：如接入外部 HTTP 服务或对象存储，统一收敛在 `app/integrations/<领域>/` 下，对外暴露稳定服务接口，业务模块不直接散落构造底层客户端。
- **按需拆分**：复杂模块按职责拆分子模块，不为了形式统一机械创建空的 service、repository 或 interface。

## 二、配置、日志、异常与类型

- **集中配置**：所有环境配置、连接池、超时与密钥统一从 [config.py](../api/app/core/config.py) 的 `settings` 获取，不得硬编码在业务模块。
- **日志规范**：统一使用 [logging.py](../api/app/core/logging.py) 配置的 `logger`；日志记录定位问题所需的业务标识，**严禁记录密码、Token、完整密钥、连接串或敏感请求正文**。
- **异常处理**：
  - 业务层使用有语义的异常或 `ValueError` 表达可预期失败。
  - API 层将业务失败映射为准确的 4xx / 5xx HTTP 状态，面向用户的错误提示使用直接、可操作的中文。
  - 禁止用宽泛的 `except Exception` 静默吞掉失败；未处理异常交由 [exception_handlers.py](../api/app/core/exception_handlers.py) 统一兜底并记录日志，不向客户端暴露堆栈或 SQL。
- **注释与类型**：
  - 公共函数、复杂内部函数和有状态类存在非直观契约时维护简洁的中文 docstring（说明参数约束、返回值、重要异常或状态变化）；显然的薄包装不写模板注释。
  - 修改签名、返回结构或异常行为时同步更新注释与类型注解；API 边界优先使用 Pydantic 模型，内部动态数据库行可保留 `dict[str, Any]`。

## 三、API 与契约规范

### 1. 路由与统一响应

- 新增业务 `APIRouter` 需在 [main.py](../api/app/main.py) 注册并统一挂载 `settings.API_PREFIX`（默认 `/api/v1`），定义稳定的前缀与 `tags`；已有 router 新增端点无需重复注册。
- 路径遵循资源语义；分页查询保持 `pageNum`、`pageSize` 参数名，查询参数通过 FastAPI / Pydantic 声明边界。
- 普通 JSON 业务接口统一使用 `ApiResponse[T]`（[schemas/response.py](../api/app/schemas/response.py)）与 `success(data, message)`（[utils/response.py](../api/app/utils/response.py)）：

```json
{
  "code": 200,
  "message": "success",
  "data": {}
}
```

- 分页数据统一为 `{ "list": [...], "total": 0 }`；创建接口可返回 HTTP `201`，无内容业务成功仍使用统一响应体；文件下载等二进制响应保留对应媒体类型，不包装 JSON。

### 2. 请求追踪（`X-Trace-Id`）

- [tracing.py](../api/app/core/tracing.py) 为每个进入追踪中间件的 HTTP 请求生成 32 位小写十六进制标识，通过 `X-Trace-Id` 响应头返回，不采用客户端传入的同名头；CORS 通过 `expose_headers=["X-Trace-Id"]` 暴露。
- 应用日志与数据库失败诊断沿用当前追踪标识；登录与操作审计记录保存 `trace_id`，支持按完整标识精确排查。
- 前端 [request.ts](../web/src/utils/request.ts) 统一返回 `{ ok, data, msg, code, traceId }`，调用方必须检查 `res.ok`，不得绕过请求层或假定成功。

### 3. 日期时间契约

- `created_at`、`updated_at`、登录与操作审计等真实时刻字段统一按 UTC 存储，API 返回带 `Z` 或明确偏移的 ISO 8601 字符串。
- 前端统一通过 [datetime.ts](../web/src/utils/datetime.ts) 转换本地时区展示，查询 UTC 时间范围前须先转换为带时区偏移的 ISO 8601；FastAPI 使用 `datetime` 接收，service 归一为 timezone-aware UTC 参数后绑定查询。

### 4. HTTP 错误语义

| 状态码 | 适用语义 |
| --- | --- |
| `400` | 输入组合或业务前置条件不合法 |
| `401` | 未登录、Token 无效或已过期 |
| `403` | 已登录但缺少所需操作权限 |
| `404` | 当前用户作用域内资源不存在 |
| `409` | 资源状态或唯一性冲突（如重名、重复绑定） |
| `502` / `503` / `504` | 上游外部服务协议错误、不可用或超时 |

## 四、数据库与事务规范

本项目使用 **SQLAlchemy Core 执行参数化原生 SQL**，不建立 ORM 实体映射；PostgreSQL 为唯一支持的数据库。

### 1. 数据访问边界

所有业务数据访问统一经由 [session.py](../api/app/db/session.py)：

- 请求内查询：`fetch_one_in_session`、`fetch_all_in_session`
- 请求内写入：`execute_in_session`、`insert_in_session`
- 需要原子回读写入结果：`execute_returning_one_in_session`、`execute_returning_all_in_session`
- 请求外独立会话：`fetch_one`、`fetch_all`、`execute`
- 会话级 advisory lock：`pinned_session()`（确保跨语句绑定同一物理连接）

### 2. SQL 编写规则

- **全量参数化**：所有值必须使用命名占位符（如 `WHERE id = :id`）并通过字典传参；严禁将用户输入、筛选值、排序字段或 ID 直接拼接进 SQL。
- **动态子句白名单**：动态 `IN` 为每个元素生成独立占位符；动态排序字段必须来自固定白名单映射。
- **标识符与回读**：PostgreSQL 标识符保持全小写，保留字表名使用双引号（如 `"user"`、`"menu"`）；需要回读主键的 `INSERT` 必须显式写出 `RETURNING id`（`insert_in_session` 会强制校验），禁止依赖 `lastrowid`。
- **类型策略**：
  - 自增主键使用 `BIGINT GENERATED BY DEFAULT AS IDENTITY`；静态数据显式指定 ID 后同步 `setval`。
  - 布尔值使用原生 `BOOLEAN`（`TRUE` / `FALSE`）；JSON 文档使用 `JSONB` 并通过 `jsonb_param()` 显式适配 Python `dict`/`list`。
  - 时刻统一使用 `TIMESTAMPTZ`（数据库连接会话固定为 UTC），直接绑定 timezone-aware `datetime`，禁止传无时区字符串依赖隐式 `CAST`。
  - 非负整数使用 `CHECK (column >= 0)` 表达约束。

### 3. 事务与并发

- 单条独立写入可使用默认自动提交；**多表或多步骤变更必须共享同一 `Session`**，各步传入 `commit=False`，由调用方统一 `db.commit()`，异常路径必须 `db.rollback()`。
- 避免在循环中无必要地逐条提交；更新并回读最新状态/计数优先使用单条 `UPDATE ... RETURNING`。

### 4. 结构基线、版本迁移与数据生命周期

- **双轨同步维护**：任何表结构、索引或静态种子变更，必须同时更新新库基线 [init.sql](../api/app/db/init.sql) 并在 `api/app/db/migrations/` 新增版本迁移脚本及更新 [init_db.py](../api/app/db/init_db.py) 的版本升级逻辑。
- **保留已发布迁移**：已发布的迁移脚本不可修改、重命名或删除；每条 SQL 以英文分号结束，尽量保持幂等。
- **用户数据生命周期**：新增用户所属业务表或关联数据时，必须同步评估并实现用户删除时的清理/转交/保留策略与外键约束，避免遗留孤立私有数据。

## 五、安全与鉴权规范

- **敏感信息零提交**：`.env`、`SECRET_KEY`、`POSTGRES_PASSWORD` 等凭证严禁提交到仓库；生产环境必须替换示例值，前端 `VITE_*` 严禁存放密钥。
- **密码与会话**：前端登录前经 [password.ts](../web/src/utils/password.ts) 做 SHA-256 摘要，后端在 [security.py](../api/app/core/security.py) 使用带随机盐的 PBKDF2-SHA256 持久化；JWT 通过 `Authorization: Bearer` 传递。
- **后端为唯一授权边界**：
  - 受保护接口必须声明 `get_current_user`；需要细粒度授权的接口使用 `require_permission("domain.action")` 或 `require_any_permission(...)`，权限键必须在 [catalog.py](../api/app/modules/access_control/catalog.py) 统一登记。
  - `role_menu` / 菜单授权仅控制导航展示，不替代 API 操作权限；查询与修改资源时必须校验当前用户作用域，避免仅按 ID 越权操作。
- **审计与脱敏**：管理类写操作按需声明 `operation_log("操作标题")`；数据库引擎开启 `hide_parameters=True`，日志与审计不得记录密码、Token 或完整密钥；生产环境 CORS 仅配置所需 Origin。

## 六、验证原则

- **针对性最小充分验证**：只验证本次改动直接涉及的接口、权限边界、异常映射与数据库初始化/升级路径，不盲目运行无关模块测试。
- **契约联动检查**：接口入参、响应结构或权限键变更时，同步核对 `web/src/api/*.ts` 调用方与前端类型检查（`npm --prefix web run typecheck`）。
- **纯文档修改**：仅核对链接、标题与源码依据，不执行无关业务测试。
